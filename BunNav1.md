# BunNav1: Excel navigation protocol (tool-based)

## Purpose
Answer a point query from an xlsx file cheaply. Use only the thirteen tools provided — `list_sheets`, `get_dims`, `set_terms`, `map_block`, `map_bin`, `peek_ascii`, `check_axes`, `peek_axes`, `peek`, `peek_row`, `peek_col`, `all_axis`, `read_cell`. Every tool call costs money: this conversation's full history is resent to the model on every turn, so an oversized or unnecessary call gets paid for again and again, not once. Read exactly what you need, nothing "for context." Number cell values are always shown capped to 3 significant figures — that's a display cap, not the real precision.

## Shared flag vocabulary
Four tools share one flag vocabulary, computed by the same classifier at scan time:
- `D` — date-like (matched a period-string pattern, e.g. `"2Q21"`, `"2022E"`, `"FY2017"`, or the cell is a native Excel date/time value). Always computed, independent of query.
- `A` — matches your `metric_term`, if you supplied one.
- `B` — matches your `entity_term`, if you supplied one.
- `C` — matches your `year_term`, if you supplied one (an integer year — e.g. `2022`). Recognizes years embedded in period strings (`"FY3/22"`, `"1Q22"`, `"2022E"`, `"2022年末"`, `"YE2022"`, etc.), native dates, and plain numeric year cells. Narrows to the right year among many `D`-flagged period columns — it does not narrow to a specific month/quarter within that year.

`metric_term`/`entity_term` are plain case-insensitive substring matches against cell text — not literal fuzzy/edit-distance matching. Pick short, distinctive substrings from the question (e.g. `"Wafer"`, `"300mm"`), not whole phrases. `year_term` is a plain integer, not a substring — pass the calendar or fiscal year the question is actually asking about.

Each tool aggregates and renders this vocabulary at a different resolution — sheet-level counts, block-level counts, bin-level presence flags, or per-cell letters. If a cell matches more than one condition (e.g. a cell reading `"300mm wafer"` matches both a metric term and an entity term), sheet/block/bin counts and flags treat `D`/`A`/`B`/`C` as independent — the same cell can count toward more than one. Only `peek_ascii`'s single-letter-per-cell rendering has to pick one; there the priority order is metric (`A`) > entity (`B`) > year (`C`) > date (`D`) > plain (`S`/`N`) — query-relevance outranks generic type info, since the tool is being consulted specifically to answer that query.

## Tools
- `list_sheets(metric_term?, entity_term?, year_term?)` — sheet names + visible/hidden state. Always call first; use the exact name returned. With `metric_term`/`entity_term`/`year_term`, also scans every visible sheet and adds raw `D` count (always), `A`/`B`/`C` counts (only for terms you supplied), plus `scanned_rows`/`scanned_cols`. A key is omitted, not shown as `0`, if you didn't supply that term. These are **raw counts, not a ranking score**. A sheet scanned only partially (>10,000 true rows) carries a `note` naming rows remaining, and the call's own `sheets_not_fully_scanned` field lists every sheet that happened to. Omit a term arg to use whatever `set_terms` has set; pass one explicitly to override for this call only.
- `get_dims(sheet)` — `max_row`/`max_col`. Treat as an upper bound only — formatting artifacts often overstate the real extent. Confirm with `map_block` or `map_bin`.
- `set_terms(metric_term?, entity_term?, year_term?)` — fix your query terms once for the rest of this session. `list_sheets`/`map_block`/`map_bin`/`peek_ascii` all fall back to whatever's set here whenever you omit their own term args, so you stop retyping the same 2-3 strings on every call. Call it right after you've picked your terms (typically right before or after your first `list_sheets`), and again only if you deliberately pivot to a different query. Returns the full current state (`metric_term`/`entity_term`/`year_term`, all three) so you can confirm what's active. `check_axes` has no term args of its own at all — it reads session state unconditionally, so call `set_terms` before your first `check_axes` call or its interior-cell flags will be meaningless.
- `map_block(sheet, metric_term?, entity_term?, year_term?)` — **default first structural call**, before `map_bin`. Finds every table block on the sheet (column bands split by fully blank columns, then row blocks split by fully blank rows within each band) and renders a compact line list: one entry per block, with its exact row/col range, raw `D`/`A`/`B`/`C` counts over that range, and two more columns, `AB-run`/`CD-run`. Blocks separated by only 1-3 blank rows in the same column band are merged into one entry, shown with a dash-range block number (e.g. `1-3`) — that's your signal more than one real block is bundled there, not a renumbering. A block that didn't merge keeps its own single number. No size/cell-count field — if a single entry is too big for one `peek_ascii` call, just peek it in two calls, or use `peek_row`/`peek_col` instead (see below).
  - `AB-run`/`CD-run`: any unbroken run (length >= 3) of lineitem-hits (`AB-run` — a metric/entity match, or a plain string sitting next to a real match) or period-hits (`CD-run` — a date-like cell, or a plain string sitting next to a real one) found in that block. Each candidate is `<index><r|c>` — `r` row-form, `c` col-form — comma-joined, up to 5 shown, `-` if none. A block whose raw candidate count runs far past 5 (a dense data column repeatedly matching, not a real header) gets flagged in `notes` to investigate rather than trusted at face value. A candidate list mixing orientations (e.g. `2c,5r`) is flagged too — more likely one is a stray false positive than a genuinely dual-orientation axis; order does not imply nesting when orientations mix.
  - **If a block shows a candidate in both `AB-run` and `CD-run`: you have everything `check_axes` needs — its `tags`/`rows`/`cols` args are copied straight off that one table row.** No need to call `map_bin` or blind-sweep `peek_ascii` first.
  - **If a block shows a candidate in one column but `-` in the other:** the missing axis is likely not absent from the sheet — check earlier blocks in the same table for an entry sharing the same `cols` range with a populated candidate in the missing column (common in repeated-section layouts, where a period header is stated once near the top and every data block below inherits it without restating it).
  - **If a block shows `-` in both columns**, and no earlier same-`cols` block supplies either axis: falls back to the manual path below (`map_bin`/`peek_ascii`/`peek_row`/`peek_col`).
- `map_bin(sheet, metric_term?, entity_term?, year_term?)` — coarse, whole-sheet, uniform 10x10-cell bins. **Call this only after `map_block`, and only if its flat list doesn't answer a spatial/relative-position question** (role-swap headers, transposed axes, comparing two column bands side by side) — a grid conveys relative position that a line list can't. Each bin renders as a **5-character code**: position 1 is structural (`.` blank bin, `:` content but not a corner, `#` a block's exact top-left corner), positions 2-5 are `D`/`-`, `A`/`-`, `B`/`-`, `C`/`-` — the letter if that condition is true anywhere in the bin, else `-`. A blank bin is always `.----`. Real row/col numbers label each bin boundary — use them directly as coordinates into `peek_ascii`. This is coarse — it tells you *where* to look and roughly *what kind of content* is there, not exact values.
- `peek_ascii(sheet, r0, r1, c0, c1, metric_term?, entity_term?, year_term?)` — full-resolution step between `map_block`/`map_bin` and `peek`. Renders the actual cell-*type* grid (not real values), one letter per cell: `.` blank, `A` metric-term match, `B` entity-term match, `C` year match, `D` date-like, `S` string, `N` number, `?` other (priority order `A` > `B` > `C` > `D` > `S`/`N`/`?` if more than one applies). Use it to find the header row inside a block/bin: a dense run of `D` is very likely the period axis, regardless of where it sits; a dense run of `C` narrows that to the specific year the question asks about. A dense run of `A`/`B` narrows straight to the rows/columns your query terms actually hit. Any of these is a density signal, not a verdict — confirm with `peek` before trusting it. If the requested window is too large, it's clamped rather than rejected — you still get data back, plus a `note` naming the actual range shown; a follow-up call for whatever the note says is missing costs less than guessing a smaller window blind.
- `check_axes(sheet, tags, rows, cols)` — confirm a `map_block` `AB-run`/`CD-run` candidate is a real axis before reading it. `tags`/`rows`/`cols` are copied verbatim off one `map_block` output row (e.g. `tags=["3r","7c"]`, `rows="3-6"`, `cols="2-7"`) — no term args, it reads whatever `set_terms` set. Renders the block (tag-centered, expanded, clamped only over 225 cells): any cell in a tagged row or column shows its **real value**; every other cell shows `peek_ascii`'s type flag. Raw row/col numbers always label the grid — **but don't count grid columns by eye to read a value off it.** On a wide grid (many columns, or one very wide tagged column next to narrow ones) the header's index numbers end up unevenly spaced, and miscounting by one column is a real, measured failure mode. Use the response's separate `tagged_values` field instead — it restates every tagged row's/column's own values as an explicit `{index: value}` dict, same shape as `peek_axes`. Read the grid only for the pattern question (does real data actually line up under both axes); read `tagged_values` for the actual number. Also auto-pulls in the row immediately above a tagged row (or column immediately left of a tagged column) when it looks like a header, even if `map_block` never flagged it — a coarser nested header (year sitting above quarter) is often too sparse for the run detector to catch on its own; a `note` says when this happened. Degrades cleanly to an empty response when the sheet genuinely has no consistent axis there (e.g. a Peak/Trough date column that changes every row) — that's correct behavior, not a gap; fall back to `peek`/`peek_ascii`.
- `peek_axes(sheet, tags, rows, cols)` — read a confirmed candidate axis's own real values, no grid, no flagging. Same `tags`/`rows`/`cols` sourcing as `check_axes`, but here `rows`/`cols` only bound the scan range per tag, they don't define a rendered window — a row's or column's own real values stay small (only the non-blank cells) even inside a huge block, so this stays cheap where `check_axes` would need clamping. Returns one line per tag, `{index: value}`, sparse, each with its own independent truncation cap — nothing pulled in beyond what you asked for. Use this once a candidate is confirmed (via `check_axes`, or trusted directly when `map_block` returned only one clean candidate) and you just need its values, not a structural check.
- `peek(sheet, r0, r1, c0, c1)` — read real values in a small window. If the requested window is too large, it's clamped rather than rejected — same behavior as `peek_ascii`, data plus a `note` naming the actual range shown. Use it once `peek_ascii` (or a `map_block`/`map_bin` flag) has pointed you at a specific row/column to confirm what's actually there.
- `peek_col(sheet, row, col)` / `peek_row(sheet, row, col)` — confirm one lineitem's or period's neighbors without a whole-axis dump: anchor on a single cell (a candidate label or a candidate period cell you already have coordinates for, e.g. from `map_block` or an earlier `peek`), and get every value along that cell's own column (`peek_col`) or row (`peek_row`) within its containing table block — you don't need to call `map_block` first, the block is found the same way. Returns `{"values": {index: value}}`, sparse (blanks omitted), plus a `note` whenever the block was too big to show in full (windowed ±20 around your anchor instead), your anchor's own axis is blank throughout (wrong anchor — the real label/period lives in a neighboring column/row), or output length still needed trimming. Prefer this over `all_axis` for "is this the right column/period" questions — it's scoped to the one block that actually matters, not the whole sheet.
- `all_axis(sheet, kind, index)` — `kind` is `"row"` or `"col"`. Dumps every non-blank value along that full row or column — the deliberate whole-axis option, for when you genuinely need it (not just to confirm one neighbor — use `peek_row`/`peek_col` for that). Use once `peek`/`peek_ascii` has told you which row is the period header, or which column holds row labels — not before. If a `"col"` read comes back mostly numeric, it's warning you that's probably a data column, not a label column — stop and recheck rather than trusting it. Output can carry a `note` if the scan itself was bounded or if the number of values found exceeded what's returned — either way you get the real values that fit, not a rejection.
- `read_cell(sheet, row, col)` — single value. Use for the final point-query lookup(s).

## Workflow
1. `set_terms(metric_term, entity_term, year_term?)` — pick a short, distinctive term for the metric and entity in the question, and the specific year if the question names one. Fix them once; every later call below omits its own term args and falls back to these.
2. `list_sheets()` — rank candidate sheets by count vs. size, not raw count alone. If you need to know the sheet size, `get_dims`.
3. `map_block(sheet)` — default first structural call. Look at which block(s) carry `D`/`A`/`B`/`C` counts, how big each block's row/col range is, and whether `AB-run`/`CD-run` already name a candidate.
   - Both columns populated on one block: skip straight to step 5 (`check_axes`) with that row's `tags`/`rows`/`cols` — steps 4/5a below aren't needed.
   - One column populated, the other `-`: check earlier blocks sharing the same `cols` range for the missing axis before falling back further.
   - Both `-`, no earlier block supplies either: continue to step 4.
4. `map_bin(sheet)` — only if `map_block`'s flat list doesn't resolve a spatial/relative-position question (role-swap headers, transposed axes, comparing adjacent column bands). Not a required step.
5. Confirm a candidate axis:
   - `check_axes(sheet, tags, rows, cols)` — a `map_block` row named a candidate on at least one axis, and you want to verify it against its neighbors/the other axis before trusting it. Copy `tags`/`rows`/`cols` straight off that table row.
   - `peek_axes(sheet, tags, rows, cols)` — you already trust the candidate (confirmed by `check_axes`, or `map_block` returned only one clean candidate) and just need its values.
   - Neither found anything usable: `peek_ascii` a candidate block/bin to see cell-type density without spending a `peek` call — look for a dense run of `D` to find the period header row, a dense run of `C` to land on the specific year, a dense run of `A`/`B` to find where your query terms actually land, or a dense run of `S` in one column for the label column.
6. `peek` the specific row/column step 5 pointed at to confirm real values (header text, label text), if `check_axes`/`peek_axes` didn't already give you enough. Once you have one candidate cell (a lineitem label or a period cell), `peek_row`/`peek_col` on it confirms its neighbors — siblings in the same lineitem block, or the rest of the same period header row — cheaper than a full `all_axis` dump when you only need to check nearby cells, not the whole axis.
7. `all_axis` to confirm the full period axis and/or row-label axis, once you know which row/column they are and genuinely need every value on it.
8. `read_cell` for the target data point(s).
9. If the requested figure isn't a direct cell (e.g. a CAGR column exists but is blank for this row), pull the two endpoint values with `read_cell` and compute the figure yourself in your answer — no tool call needed for arithmetic.

## Judgment checklist (known failure modes)
- To find *which* row or column among many matches your metric/entity/year term — not to confirm one you already have coordinates for — scan candidate windows with `peek_ascii`'s `A`/`B`/`C` flags instead of guessing rows with `peek_col`/`peek_row`; `check_axes`/`peek_axes` need a specific row/col already in hand and won't search for one.
- Match a header to its value by shared column number, never by counting position across a row.
- The header row is not always the top row of a block — there may be a title row above it. This is exactly why the workflow scans for `D` density with `peek_ascii` instead of assuming the header sits at a block's top row.
- A single `D` cell near a real header is not necessarily part of the period axis — check whether data actually populates under it before trusting it.
- `D` density is a signal, not a classifier: a year can be stored as a plain number (`N`, not `D`) in one column and as a string (`D`) in the next — don't rule out a numeric-typed period row just because it shows `N` instead of `D`. `C` (year match) does see plain numeric year cells, unlike `D`.
- `C` matches on year only, never month/quarter — if a period header is monthly (e.g. twelve native-date columns for one year), every column sharing the target year flags `C`, not just the one you need. `C` narrows candidates, it doesn't uniquely identify the column by itself.
- A CAGR/range column (e.g. `"2019-21"`) or a scenario label (e.g. `"Bull '24E"`) will also flag `D` — that's correct, it contains a period reference, not necessarily a repeating period header. `C` deliberately does *not* match range-style periods like `"2019-21"` (it only matches an exact year, not range membership) — don't expect `C` to fire there. Verify with `peek`.
- `A`/`B` are plain substring matches, not semantic understanding — a generic term that's the sheet's own subject (e.g. "Wafer" on a wafer supply/demand sheet) will match everywhere and give weak disambiguation no matter how it's rendered; and an unrelated cell can match by coincidence (e.g. an entity term "Cell" matching a "Miscellaneous Assets" block, or an instructional footnote). A match is a candidate location, not a confirmed answer — always confirm with `peek`.
- `A`/`B` only match the literal substring given — a non-Latin-script rendering of the same term (e.g. a Japanese-language mirror column) won't match an English `metric_term`/`entity_term`. Don't conclude "not here" from an all-`-` region without checking whether the sheet has a same-content column in another language.
- Row labels can be nested across multiple columns — check more than one column before committing to "the" label column. If a lineitem-label anchor comes back blank throughout via `peek_col`, that's telling you the real labels live in a neighboring column, not that the block has no labels.
- An all-text row with no numbers can be a blank spacer, not a section header — don't infer meaning from shape alone.
- A data block can share a header row with the block above it if `map_block`/`map_bin` split them at a blank row — check upward if a block has data but no header of its own.
- One header row can serve several disconnected blocks below it, not one header per block — don't assume every block needs its own `peek_ascii`/`peek` pass if an earlier one already covers it.
- Derived columns (CAGR, YoY%, etc.) are sometimes populated for only some rows in a sheet — a blank cell there doesn't mean the figure doesn't exist, it may mean you compute it from two endpoints (workflow step 9).

## Constraints
- If you have more than one call queued and none of them depends on an earlier one's result (e.g. `set_terms` followed by `list_sheets`, or `check_axes` on two different candidate blocks from the same `map_block` output), issue them together in the same turn instead of one at a time — this session's full history resends on every turn, so every extra round trip is paid for again on every later turn, not once.
- Every tool call is expensive — this session's entire history resends on every turn. Don't call a tool "just to see" or "for context" once you already have your answer.
- Never re-request a range you've already read — check your own earlier tool results before calling again. A repeated identical call will be flagged, not re-executed.
- You have a hard budget of tool calls this session. Reaching the answer efficiently is graded, not just reaching it at all.
